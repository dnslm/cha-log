# Процесс работы

Проект ведётся один, но по правилам командной разработки: так видно историю решений и набирается практика, которая пригодится в команде.

## Ветки (GitHub Flow)

- `main` всегда рабочая. Напрямую в неё не коммитим, только через Pull Request (PR).
- Для каждой задачи своя короткая ветка от свежего `main`.
- Именование: `тип/номер-issue-краткое-описание`, например `feat/12-tea-crud`, `fix/31-rating-rounding`, `docs/5-readme`.

```
main ──●───────────●────────────●──
        \         /              
         feat/12-tea-crud ──●──●
```

## Цикл одной задачи

1. Создать (или выбрать) issue на доске и перенести его в **In progress**.
2. Обновить `main` и создать ветку:
   ```
   git switch main
   git pull
   git switch -c feat/12-tea-crud
   ```
3. Сделать работу небольшими коммитами.
4. Отправить ветку: `git push -u origin feat/12-tea-crud`.
5. Открыть Pull Request. В описании написать `Closes #12`, тогда issue закроется автоматически после слияния.
6. Дождаться зелёного CI, просмотреть свой diff во вкладке **Files changed**, поправить замечания к самому себе.
7. Влить PR кнопкой **Squash and merge** (вся ветка превращается в один аккуратный коммит в `main`) и удалить ветку.
8. Локально: `git switch main && git pull`.

## Коммиты (Conventional Commits)

Формат: `тип(область): краткое описание в повелительном наклонении`.

| Тип | Когда |
|-----|-------|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `docs` | только документация |
| `test` | тесты |
| `refactor` | изменение кода без изменения поведения |
| `chore` | настройка, зависимости, служебные файлы |
| `ci` | GitHub Actions и всё про пайплайн |

Примеры: `feat(api): add GET /api/teas`, `fix(ui): round half stars correctly`, `ci: run tests on pull requests`.

Рекомендация: код, имена веток и коммиты на английском (так принято в индустрии), документация и интерфейс на русском. Это можно поменять, главное придерживаться единого выбора.

## Доска задач: GitHub Issues + GitHub Projects

Лучше использовать их вместе, это не два разных подхода. **Issues** хранят сами задачи, а **Projects** показывают их как канбан-доску.

Почему именно так:

- Issue связывается с веткой, PR и коммитами, а при слиянии PR с `Closes #N` закрывается сам.
- Доска Projects строится прямо на твоих issues, отдельных карточек вести не нужно.
- Всё лежит рядом с кодом, и по истории видно, как шла работа.

### Настройка доски

1. На странице репозитория: **Projects → New project → Board**. Название, например, «Чайный дневник».
2. Колонки (поле **Status**): `Backlog`, `Todo`, `In progress`, `In review`, `Done`. Лишние можно удалить, недостающие добавить в настройках поля Status.
3. Включить встроенные автоматизации (**Workflows** в настройках проекта): закрытый issue → `Done`, новый issue → `Backlog`.
4. Подключить репозиторий и добавлять issues на доску.

### Правила

- **Размер задачи**: от 1 до 3 часов работы. Если больше, разбить на несколько issues.
- **WIP-лимит**: в `In progress` не больше 1–2 карточек. Сначала закончить, потом начинать новое.
- **Backlog** хранит идеи и будущие этапы, **Todo** задачи на ближайшие 1–2 недели.
- **Один issue, один PR.**
- Раз в неделю: быстро просмотреть доску, переставить приоритеты, перенести мелкие идеи из головы в Backlog.

### Метки (Labels)

| Группа | Метки |
|--------|-------|
| Тип | `enhancement` (фича), `bug`, `documentation`, `chore` |
| Область | `frontend`, `backend`, `db`, `ci` |
| Особые | `learning` (задача про изучение чего-то нового), `blocked` |

### Вехи (Milestones)

По одной на этап дорожной карты: «Этап 0. Старт», «Этап 1. Бэкенд и БД» и так далее. Так виден прогресс в процентах.

## Защита ветки main

**Settings → Rules → Rulesets → New branch ruleset** (или классические Branch protection rules в **Settings → Branches**). Цель: ветка по умолчанию.

- Require a pull request before merging. Количество одобрений оставить 0, ведь собственный PR самому себе не одобрить.
- Block force pushes.
- Require status checks to pass. Включить после первого запуска CI, потому что названия проверок (`Backend (lint + test)` и `Frontend (lint + test + build)`) появятся в списке только после запуска workflow.
